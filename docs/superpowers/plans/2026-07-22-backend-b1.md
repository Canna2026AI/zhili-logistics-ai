# Backend B1 Domains Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在三个无重叠工作树中实现身份主数据、报价订单运单、仓库干线尾程的真实数据库与 OpenAPI handler，使五端关闭 Mock 后完成核心跨端流程。

**Architecture:** 每条分支只写自己的 `packages/features/<domain>/src/backend` 与 `apps/api/src/modules/<domain>`；数据库变更先写 `docs/03-delivery/schema-proposals/<branch>.sql`，由根集成负责人一次合入 `packages/db/src/schema` 并生成迁移。领域服务通过显式应用端口协作，不跨包导入内部文件。

**Tech Stack:** Backend Foundation、生成 OpenAPI 类型、Drizzle、Vitest + fast-check、Testcontainers、Supertest/Undici。

## Global Constraints

- 分支：`codex/backend-identity-masterdata`、`codex/backend-rates-waybills`、`codex/backend-warehouse-linehaul`。
- 每个 mutation 同事务写领域状态、审计和 Outbox；权限失败不得产生任何三者。
- Controller 不定义重复 DTO；handler 输入输出必须 `satisfies` 生成 OpenAPI 类型。
- 每个聚合按 `tenant_id + id` 查询并校验版本；跨租户一律表现为 404 或策略规定的 403，禁止泄露存在性。
- 所有列表使用稳定游标，排序键至少含唯一 ID；批量命令逐项返回真实结果。

## Execution Order

为消除 Task 1“先收齐提案”与 Task 2–4“在领域分支创建提案”之间的依赖环，B1 固定分成两个并行阶段：

1. 从同一主分支提交创建三个领域工作树；每个工作树先只提交、测试并独立审查自己的
   `docs/03-delivery/schema-proposals/*.sql`，不得修改 `packages/db`、迁移序列或生成契约。
2. 根集成负责人收齐三个已审查提案后执行 Task 1，只在主分支生成统一 Drizzle schema 与
   `0001_b1_domains.sql`，完成 migration up/down/up、RLS 与 schema fingerprint 门禁。
3. 三个领域工作树同步根 schema 提交后，再并行完成 Task 2–4 的 repository、service、controller
   与领域测试；仍不得自行新增或重排迁移。
4. 每个领域通过独立 0 Critical / 0 Important 审查后，按 Task 5 的固定顺序回并主分支。
